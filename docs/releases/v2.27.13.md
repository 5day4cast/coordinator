# v2.27.13 — Writes wait for SQLite's lock, and freed memory goes back after bursts

Every transaction on the write pool now begins with `BEGIN IMMEDIATE`.
A deferred transaction that read before it wrote asked for the write lock only at its first write, and when another process held the lock SQLite refused it at once without waiting out the busy timeout.
That is how two successful Lightning payouts went unrecorded until the payout watcher's next sweep; entry admission, ticket reservation, queued reservation, pool formation and ticket registration had the same pattern.
A payment outcome write that is refused before it runs (lock still held, or the write queue full) is tried again after 250 ms and then 1 s; the writes are idempotent, and the watcher still records an outcome refused every time.
`coordinator_payment_persist_failures_total{reason="busy|queue_full|error"}` counts every refused write.

The coordinator returns freed heap memory to the system after bursts.
Memory in use falls back after every kickoff, payout and refund, but glibc kept each burst's peak, so the process held over a gigabyte of free arena space that ended up in swap.
A background task calls `malloc_trim(0)` once resident anonymous memory plus swap has grown by 64 MiB since the last trim and stopped growing.
`coordinator_allocator_trims_total` and `coordinator_allocator_trimmed_bytes_total` count trims and the memory they released; peak memory during a burst is unchanged.

No configuration or storage changes. The verifier enclave is unchanged; keep the deployed verifier artifact.
