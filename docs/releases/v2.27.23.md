# v2.27.23 — Bound and count Ark indexer requests

Failed payment reconciliation could call `GetVtxos` every second. Those reads were not logged at info level, so operators could not count outbound requests from application logs.

This release adds a shared request guard to each process. Requests to the same indexer endpoint run one at a time, with at least two seconds between a successful response and the next request. Failed or cancelled requests use exponential backoff with jitter: 10–20 seconds initially, rising to 150–300 seconds. Queued requests have a deadline and do not send when that deadline expires.

Swapd also persists payment and refund lookup backoff in SQLite. Concurrent workers cannot reserve the same lookup, and restarting the service preserves that schedule. Missing settled VTXOs use jittered retries as well. Migration `0007_indexer_backoff.sql` runs automatically at startup.

Coordinator, swapd, and Synth now log each dispatched SDK `GetVtxos` request at info level with `ark_indexer_request protocol=grpc method=GetVtxos`. Synth uses the same guard for its REST indexer reads and logs each page with `protocol=rest`. Swapd exposes its process counter through authenticated `GET /v1/indexer/stats`; this route does not contact the indexer. Counts describe dispatched attempts, including failed calls, and do not prove receipt by the provider.

Deploy all three services to cover their traffic. The guard is per process and endpoint; it does not impose one shared limit across multiple processes or hosts. Transport counters and transport backoff reset when a process restarts. Swapd's persisted lookup backoff survives restarts.

Regression tests exercise 100 concurrent callers, unavailable upstreams, cancellation, pagination, empty lookups, and database reopen. Local validation passed 451 tests, with one existing ignored test. Synth's full suite passed with serial execution after timing failures during parallel execution.
