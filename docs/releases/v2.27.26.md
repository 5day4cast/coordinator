# v2.27.26 — Stop re-reading the Ark wallet's history

For every `GetVtxos` listing by address, the indexer reads every VTXO the address has ever held, then filters and pages the result in memory. A page only shortens the reply. A wallet that has paid escrows for weeks holds thousands of spent VTXOs. Each wallet reading made the indexer read all of them twice, once for spendable and once for recoverable. Each board or renewal walked the whole history 100 VTXOs a page.

Under the shared budget from v2.27.25, ten requests per four minutes with background work stopped at four, a renewal or board of such a wallet could not finish: its listing needs a reservation for each of its pages. Renewals keep the wallet's coins payable, so a wallet that cannot renew stops paying escrows once its coins come within the pay margin of expiry.

- **Boards and renewals list unspent VTXOs only.** In the rust-sdk fork, `settle` and the batch input selection ask the indexer for unspent VTXOs (`renewable_only`) instead of the whole history. Each now takes a request or two. The client-side selectors still decide what settles, so a server that ignores the filter gives the same result.
- **Wallet readings list only what changed.** swapd keeps its unspent VTXOs between readings. It lists them in full (unspent only, one request) when it starts and every 30 minutes. In between, each reading asks only for the VTXOs created, spent, settled or unrolled since the last one, reaching five minutes further back for clock skew. The time bound is the one part of a listing the indexer's query applies. A sweep is not one of those changes, but it happens at expiry, which the coin classification reads from the VTXO itself. A reading takes one request where it took two.
- Escrow payment lookups are unchanged. Each swap pays its own escrow address, whose history is one or two VTXOs.

Tests cover the `renewable_only` request and its gRPC mapping; when a full listing is due; what each listing asks for; and how a listing of changes removes spent and unrolled VTXOs and adds new ones, including changes listed twice. A full listing also drops spent VTXOs, in case a server ignores the filter.
