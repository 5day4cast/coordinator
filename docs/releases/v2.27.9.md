# v2.27.9 — Reduce checkpoint read and journal memory

Status and registration-assignment reads select authenticated checkpoint metadata before fetching part bodies.
They do not reconstruct signing journals, policies, or settlement payloads from partitioned checkpoints.
The manifest and selected parts share one database snapshot.
Credential, pinned authorization, schema, session identity, and part authentication checks remain enforced.
Legacy checkpoints remain readable; their encrypted JSON still requires full decryption.

Full partitioned recovery reconstructs JSON through a 32 KiB zeroized staging buffer instead of a whole-checkpoint plaintext allocation.
Every compressed part passes authenticated decryption, content-MAC verification, and gzip integrity checks.
Decoding must consume the final part and end of input before returning state.
The reconstructed 512 MiB size limit remains enforced, and SQL fetches use batches of at most 200 part identifiers.
Compressed part bodies, decoded state, and individual large scalar allocations still contribute to memory use.
Incremental decoding trades some CPU time for lower peak memory.

The SDK shares unchanged journal entries across enclave lanes and copies only changed outcomes.
The matching verifier enclave adds a 256 MiB preparation-reply budget shared across sessions.
Exact retries and authorized execution or recovery remain available under budget pressure.
Pressure shortens idle session retention to five minutes through the existing durable restoration path.
This is not a total enclave-memory cap.

Deploy the matching custom verifier artifact and Coordinator application together.
Checkpoint formats and compare-and-swap writes remain compatible with the previous release.
Validation covers metadata projection, concurrent writes, missing or corrupt parts, late integrity failures, size limits, and durable cryptographic recovery.
